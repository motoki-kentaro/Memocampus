### メッセージ経路（重要な設計判断）

他スレッドから UI への通知は、チャネル＋隠しウィンドウへの `PostMessageW`。スレッドメッセージにしない理由：**メニューを開いている間（モーダルループ）、スレッドメッセージは捨てられる**ため、メニュー表示中に状態が変わると反映が失われる。ウィンドウ宛なら配送される。隠しウィンドウは `WM_QUERYENDSESSION`／`WM_ENDSESSION`（ログオフ・シャットダウン）も受け取る（メッセージ専用ウィンドウは受け取れない）。

メニューのクリックは何も決め打ちしない。「サーバ起動」を押しても `Running` とは表示せず、Supervisor が `Running` を報告した時点で描画する。クリック後、チェックマークは設定値へ戻す（コントロールが自分で反転するため）。

## 4. ログオン自動起動（HKCU Run）

- `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` の値 `MemocampusTray` に、Tray 実行ファイルの**引用符付き絶対パス**（引数なし）を書く。ON で登録、OFF でこの値だけ削除。管理者権限不要。同名の値は 1 つなので重複しない。空白・日本語を含むパスをテストで確認。
- 書込み後に読み戻して確認する。読み戻せなければエラー（成功とは表示しない）。
- 設定（`tray-settings.json`）とレジストリは、**レジストリを先に変更・確認し、設定を保存する**。変更の前に Run 値の**正確な元の値**（未登録、または元の文字列）を読み取って保持し、保存に失敗したらその値へ戻して**読み戻して確認する**（独立レビュー S2-02）。
  - 元の値が読めなければ、戻せないので変更しない。
  - 戻せた場合だけ「変更を取り消しました」と表示する。戻せなかった、または読み戻しが一致しなかった場合は「設定と登録が一致していません」と表示し、状態を `registry_inconsistent` として保持する（次の成功する変更で解除）。
  - 初回登録の設定作成失敗、パス更新、登録の読み戻し失敗にも同じ処理を適用する。
- **他アプリの Run エントリは読まず、変更しない**（隔離レジストリのテストで、他の値が不変であることを確認）。
- **EXE 移動**：登録値のパスが現在の実行ファイルと異なれば「登録パスが現在の実行ファイルと異なります」と表示する。自動では直さない。ユーザーが「自動起動の登録を現在の場所へ更新」を選んだときだけ書き換える。
- **Windows 側の無効化の尊重**：`...\Explorer\StartupApproved\Run` は**読むだけ**。無効なら「Windows側で無効にされています」と表示し、ON にしても無効化を解除しない。**この PC の実値は `REG_BINARY` 12 バイトで先頭が `02`（有効）または `00`（解釈しない）**。
  - 既知の形式だけを解釈する（S2-07）：`REG_BINARY`、**ちょうど 12 バイト**、2〜4 バイト目が 0、先頭が `02`／`06` なら有効、`03` なら無効。それ以外（長さ・型・予約バイト・先頭値が違うもの。`00`、`01`、`07` を含む）は**すべて「不明」**として表示し、推測せず、書き換えない。
  - 「無効＝`03`」は公知の挙動に基づく**未検証の仮定**（この PC に無効の実例がない）で、表示にのみ使う。

### 初回登録と、テストが恒久登録を作らない仕組み

`tray-settings.json` が無い通常の製品起動（既定で `autostart=true`）でのみ、**1 回だけ** Run キーへ登録して設定ファイルを作る。次のいずれかがあると「検証用起動」として登録しない：`--registry-root`、`--selftest`、`--run-seconds`、`--log`、`--mcp-exe`、`--mcp-arg`、`--no-autostart`、`--headless`、環境変数 `MEMOCAMPUS_APP_DIR`。テストは常に隔離 app dir と**隔離レジストリ**（`HKCU\Software\MemocampusTrayTest\<id>`、テスト終了時に削除）を使い、実際の Run キーには書かない（読み取りのみ。前後で不変であることを確認）。

### 実行モードとレジストリの書込み権限（S2-01）

判定は起動直後・レジストリに触れる前に 1 回だけ行い（`tray/src/mode.rs`）、**その実行が得るレジストリ自体**を決める。`product=false` という真偽値に頼らない。

| 起動 | モード | 使うレジストリ |
|---|---|---|
| 検証用の指定が何もない | Product | 実 Run キー（書込み可）。初回登録あり |
| `--registry-root <id>`（`--selftest` を含む） | Isolated | `HKCU\Software\MemocampusTrayTest\<id>`（書込み可、終了時に削除） |
| 上記以外の検証用指定（`--run-seconds` など）または `MEMOCAMPUS_APP_DIR` | ReadOnly | 実 Run キーを**読むだけ**。登録・トグル・更新・解除はすべてレジストリ層で `PermissionDenied` |
| `--selftest` を `--registry-root` なしで | 拒否 | レジストリに触れる前に終了コード 2 |

書込み禁止は呼出し側の確認ではなく `WinRegistry` の書込み経路そのもの（`set_run_value`、`delete_run_value` と隔離用の書込み関数）にある。書込み可能な実キーの取得は `WinRegistry::product()`（Product モードだけが使う）に限る。全組合せを表駆動で検証している：入力 8 個（検証用の指定 7 つ＋環境変数 `MEMOCAMPUS_APP_DIR`）の 2^8 通り × 隔離レジストリの有無 2 通り = **512 通りの組合せ**。未使用のビットが 1 つあるためループは 1024 回だが、各組合せを**2 回ずつ**評価している（1024 通りの別々の組合せを調べているわけではない）。製品モードになるのは「指定が何もない」1 組合せだけ。

## 5. サーバ自動起動・設定

- `server_autostart=true`（既定）で、Tray 起動時に Supervisor へ Start を要求する。OFF なら起動しない。
- 設定ファイルが不正でも Start は要求し、Supervisor が `Error(SettingsInvalid)` を報告する（推測値では起動しない。Slice 1 のまま）。アイコンは赤になる。
- 拒否（Vault 未承認、ポート競合）は再試行しない。異常終了の再試行上限は Slice 1 のまま。**手動停止後に勝手に再起動しない**（selftest で確認）。
- 操作：2 つのトグル（保存）、設定ファイルを開く、設定を再読み込み、ログフォルダを開く。
  - 設定ファイルが無ければ、既定値で作ってから開く。不正なファイルは**そのまま開く**（上書きしない）。
  - 不正／未知バージョンのファイルは、トグルでも再読込でも**上書きしない**。再読込で不正なら、以前の有効な設定を使い続け、「不正」と表示する。
  - ログフォルダが無ければ作らず、その旨を表示する。開くのは `ShellExecuteW`（シェル経由ではない）。
- **設定の反映**：`listen_port`・`allow_hosts`・`vault_mode`・`pinned_vault_path` は**サーバ起動時にだけ**読まれる。変更を再読込すると、実行中なら「変更あり（サーバ再起動で反映）」と表示するだけで、**勝手に再起動しない**。2 つのトグルはサーバが読まないので再起動不要。
  - **表示の同期の契約（S2-04）**：Supervisor の設定取得元は、サーバを起動するための設定の読込みを試みるたびに、共有の `Applied`（試行の**世代番号**＋成功時に使った設定）を更新する。UI は設定値の比較ではなく世代番号の変化を見て、操作スレッドに設定ファイルの読み直し（`Resync`）を依頼し、「再起動で反映」の通知を再計算する。読み直しは書込みも再起動もせず、直前のエラー表示も消さない。
    - 設定 A で起動 → ファイルを B にして再読込（通知が出る）→ ファイルを A に戻し、**再読込せず**再起動、の場合も、A が前後で同じ値でも世代が進むので同期される（通知は消え、画面の設定は A）。以前は、適用済みの値が変わらないと同期されなかった。
    - 同じ設定を読んだ再起動でも世代は進む。読込みが失敗した試行では「適用済み設定」を空にする：サーバは推測値で起動しない（Fail-Closed、Slice 1 のまま）ので、古い設定が適用されたとは表示せず、不正な設定はそのまま「不正」と表示され、ファイルは書き換えない。
    - UI が勝手にサーバを再起動することはない。

## 6. コンソール非表示

Tray は GUI サブシステム、サーバは Slice 1 の `DETACHED_PROCESS`・管理IPC・Job Object のまま。外部シェルを経由しない。設定ファイル・ログフォルダも `ShellExecuteW`。自動テストで確認したのは、子の `console_window=false`・`console_processes=0`（Slice 1）と、Tray の起動・停止・再起動・異常終了の各経路で新しいコンソールが作られないという機械確認までで、**目視は PO の確認項目**（§10）。

## 7. 終了処理

### 通常の終了（メニューの「終了」・ウィンドウの閉じる要求）

操作の受付停止（全項目無効、ツールチップ「終了処理中」）→ **終了スレッド**（別スレッド。UI スレッドは待たず、結合もしない）が次の**両方**を待つ → 両方が正常に終わったら アイコン破棄 → ウィンドウ破棄 → ループ終了。

1. Supervisor：管理IPCで停止要求 → 終了待ち（既存のタイムアウト：8 秒、強制終了後 3 秒）。Slice 1 のまま。
2. 操作スレッド（`tray/src/quit.rs`、S2-08）：終了の開始と同時に UI が操作キューの送信側を捨てる。**すでに受け付けた書込み操作は最後まで実行される**（保存まで、または検証済みの巻き戻しまで。`Controller` の契約）。キューが空になるとスレッドは終わり、結果（正常／panic）を報告する。新しい操作は、送信側で拒否される（Gate、§7 下）うえに、キュー自体が閉じている。

終了スレッドの報告（`QuitReport`）が「**Supervisor が停止した かつ 操作スレッドが正常終了した**」ときだけ正常終了（ログ `quit_done supervisor=stopped controller=completed`、終了コード 0）。次は**正常完了として扱わない**：操作スレッドの panic（`controller=panicked`）、報告なしの終了（`lost`）、待機超過（`timed_out`。操作の待機上限は 30 秒）、Supervisor の停止処理の panic（`supervisor=failed`）。この場合はログに `quit_incomplete`、`exit=incomplete`、終了コード 7 を残す（それでもプロセスは終了する。無限に待たない）。Supervisor と操作スレッドは互いを待たないので、デッドロックしない。

**保証の範囲**：通常の終了では、進行中の「レジストリ変更＋設定保存」を中断して終了する経路は無い。**OS による強制終了、電源断、Tray の強制終了（タスクの終了）は、この保証の範囲外**：Run 値を変更して設定を保存する前にプロセスが消えると、両者が食い違ったまま残りうる（レジストリと設定ファイルをまたぐ原子性は無い）。その場合は、メニューの登録状態の表示（登録なし／登録あり）と設定のチェックの不一致として現れ、チェックを操作し直せば再び揃う。これを自動で回復する永続的な仕組み（書込み前の意図の記録と起動時の回復）は作っていない。

ウィンドウ宛ての起床通知は `Gate`（`tray/src/wake.rs`）を通す（S2-06）。**ウィンドウを破棄する経路はすべて Gate を閉じてから行う**：通常の終了（`finish`）、ウィンドウの閉じる要求 `WM_CLOSE`（既定処理に渡さず、メニューの「終了」と同じ手順へ接続する。2 回続けて来ても 1 回の終了になる。他のハンドラの処理中で受け取れなければ、処理後に自分宛てに再投函する）、起動の途中で諦める経路（`abandon`）、そして最後の網として `WM_DESTROY` でも Gate を閉じる（`GATE` はスレッドローカルで、UI の借用なしに届く）。ウィンドウハンドルは Gate の中にしか無く、「受付中 → 終了開始 → 閉鎖」の 3 状態を持つ。終了を始めると操作（クリック・スクリプト）は送信側で拒否され、ウィンドウを破棄する直前に UI スレッドが Gate を閉じる。送信と閉鎖は同じ短いロックで直列化されるので、閉鎖後にそのハンドルへ投函されることはなく（ハンドル値が再利用されても誤配送しない）、投函は待機しないのでデッドロックもしない。

ログオフ・シャットダウン（`WM_ENDSESSION`）：同じ手順を試みるが、Windows の制約に従い、OS の通知ハンドラでは**最大 2.5 秒**しか待たない（無期限に待たない）。その時間内に操作スレッドが終わっていれば通常の終了と同じ。終わっていなければ、進行中の更新を待たずにプロセスが終わるので、**通常の終了とは違い、保存まで／巻き戻しまでの保証はない**（上の「保証の範囲」と同じ残余リスク）。子の MCP は、プロセス終了時に Job Object が終了させる。Tray が異常終了しても Job により子は残らない（Slice 1 のテストを UI モードでも確認）。

## 7a. アイコンの描画状態（S2-03）

「表示すべき状態」（最新の View）と「描画に成功した状態」を分けて持つ（`tray/src/render.rs`）。アイコンとツールチップは別々に試行し、成功したものだけを描画済みとして記録する。シェルに拒否された更新は成功扱いにならず、再試行される。

- 失敗時は 500 ms 間隔で再試行する。**回数の定義（S2-09）**：イベントに伴う最初の描画は再試行ではない。その後のタイマーによる描画が「再試行」で、**最大 6 回**（最初の 1 回 + 再試行 6 回 = 計 7 回の描画）。6 回目が失敗したら諦めて（ログ `render_gave_up`）待つ。7 回目の再試行は予約されない。以前は、タイマーでの描画の後に回数を確認していたため、再試行が 7 回になっていた。
- 再試行の回数が**元に戻る**のは、(1) 新しい状態（View が変わった）、(2) 新しいタスクバー（`TaskbarCreated`）、(3) 描画の成功。諦めた後でも、新しい状態や `TaskbarCreated` でふたたび描画する。`TaskbarCreated` の 600 ms 後の再描画は、その通知が開いた回数を**消費**し、元には戻さない。再試行のタイマーがすでに設定されているときの追加のイベント描画は、回数を消費しない（タイマーは 1 本）。ロジックは `render.rs` の `Drawing`（UI は実タイマーだけを持つ）。
- Explorer の再起動（`TaskbarCreated`）を UI の隠しウィンドウも受け取り、描画済みの記録を破棄して**最新の状態**を描き直す。さらに 600 ms 後にもう一度描く。`tray-icon` 自身のウィンドウも同じ通知で、自分が保持するアイコンを再登録するが、保持するのは「更新が成功したときの値」だけなので、更新が失敗した後は古い。どちらのウィンドウが先に通知を処理しても、最後に最新の状態が描かれる。

### 既存の不安定テスト（Slice 2 の 7 件とは別）

- `running_is_reached_only_after_the_server_says_it_is_listening`（Slice 1 の Supervisor 単体テスト）：固定 8 ms の待機のあとに「まだ Starting」を期待していたが、スタンドインの待受表示は起動後 20 ms に出る。負荷時は、起動の処理が 8 ms 以内に終わらなければ Stopped、20 ms を超えれば Running になり、いずれも失敗する。製品コードの不具合ではなく、テストの時間依存。24 並列の負荷下で 360 回実行し、**修正前 64 回失敗、修正後 0 回失敗**を確認。修正はテストのみ：スタンドインに「合図があるまで何も言わない」保留を追加し、`Starting` かつ pid ありを待つ。Supervisor 本体は変更していない。
- `an_encrypted_vault_answers_the_same_over_http_as_over_stdio_and_never_without_its_key`（mcp-server）：この環境では合格する（1.48 秒）。暗号化 Vault の鍵は Windows DPAPI のユーザースコープ（`CryptProtectData`／`CryptUnprotectData`）で保護されるため、ユーザープロファイルやログオンセッションの DPAPI マスターキーを使えない環境（制限付きトークンのサンドボックス、別ユーザー、プロファイルを隔離した環境）では `ProtectorFailed` になる。**環境依存**であり、製品コードの問題とはしていない。この環境では再現できないため、原因はソースの読解による推定で、サンドボックス側での確認は**未実施**。変更していない。
